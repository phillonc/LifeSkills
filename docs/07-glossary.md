# DSDM — Glossary

A quick reference for the terminology used across this documentation.

| Term | Definition |
|------|------------|
| **AgilePF** | Agile Project Framework — the modern name for the DSDM framework, stewarded by the Agile Business Consortium. |
| **Agile Business Consortium** | The not-for-profit body that stewards and evolves DSDM. (Formerly the DSDM Consortium.) |
| **Benefits Assessment** | Post-Project product confirming whether expected business benefits were realised. |
| **Business Ambassador** | The day-to-day voice of the business within the Solution Development Team. |
| **Business Case** | The justification for the project — costs, benefits, and rationale. |
| **Business Sponsor** | Most senior project role; owns the business case and budget; ultimate decision-maker. |
| **Business Visionary** | Holds and communicates the vision for the solution and its business value. |
| **DAD** | Development Approach Definition — how quality, testing, and the build approach are handled. |
| **Deployment** | Lifecycle phase that releases an increment into operational use. |
| **DSDM** | Dynamic Systems Development Method — an agile project delivery framework. |
| **EDUF** | Enough Design Up Front — establishing firm foundations without "big design up front." |
| **Evolutionary Development** | The iterative lifecycle phase where the solution is built in timeboxes. |
| **Evolving Solution** | The developing product produced during Evolutionary Development. |
| **Facilitated Workshop** | A structured, neutrally-facilitated meeting to achieve a specific objective. |
| **Feasibility** | Lifecycle phase assessing technical feasibility and financial viability. |
| **Foundations** | Lifecycle phase establishing baseline scope, solution, and management approach. |
| **Increment** | A deployable slice of the solution delivering business value. |
| **Iterative Development** | Building via repeated build–feedback–refine cycles to converge on the right solution. |
| **MAD** | Management Approach Definition — how the project is organised, governed, and controlled. |
| **Minimum Usable Subset (MUS)** | The set of Must Have requirements without which the delivery has no value. |
| **Modelling** | Using diagrams/sketches to communicate and explore ideas cheaply. |
| **MoSCoW** | Prioritisation scheme: Must / Should / Could / Won't Have this time. |
| **Must Have** | A requirement that is non-negotiable for the current delivery (part of the MUS). |
| **Outline Plan** | High-level plan produced during Feasibility. |
| **Post-Project** | Final phase; checks realised benefits after the solution is in use. |
| **Pre-Project** | First phase; ensures the right projects are started and set up correctly. |
| **Prototyping** | Building tangible, often throwaway, versions to validate and gather feedback. |
| **PRL** | Prioritised Requirements List — the MoSCoW-prioritised scope baseline. |
| **Project Manager** | Provides high-level agile project leadership and governance. |
| **Project Review Report** | Deployment product confirming what was delivered vs. expected, with lessons. |
| **RAD** | Rapid Application Development — the historical origin context of DSDM. |
| **SAD** | Solution Architecture Definition — high-level design of the business + technical solution. |
| **Should Have** | An important requirement the solution can survive without (with difficulty). |
| **Solution Developer** | Builds the solution to the agreed quality standard. |
| **Solution Development Team** | The empowered team that produces the solution within timeboxes. |
| **Solution Tester** | Tests the solution continuously against agreed acceptance criteria. |
| **Stand-up** | Short daily team meeting to coordinate and surface blockers. |
| **Team Leader** | Servant-leader who coordinates the Solution Development Team day-to-day. |
| **Technical Coordinator** | The project's technical authority, owning architectural coherence. |
| **Terms of Reference** | Pre-Project product stating the overall objective and justification. |
| **Timebox** | A fixed period (typically 2–4 weeks) with a fixed end date and flexible scope. |
| **Won't Have this time** | A requirement explicitly agreed to be out of scope for this delivery. |
| **Workshop Facilitator** | Neutral person who plans and runs Facilitated Workshops. |
